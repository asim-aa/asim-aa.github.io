The Disclosure Verifier

An agentic system that extracts quantitative claims from SEC filing prose and reconciles them against the filing's own structured data, catching disclosure inconsistencies before anyone else cross-checks them.

RoleSolo: agent architecture, MCP tools, DSPy optimization, RLVR fine-tuning
TimelineSupportVectors AI Agents & Fine-Tuning Bootcamp capstone, Phases 0–7
StackPython · DSPy · MCP · Unsloth QLoRA · GRPO (trl) · SEC EDGAR & XBRL · pytest · GitHub Actions
View exhibit Source on GitHub

Problem

SEC filings publish the same information twice, in two formats that almost nobody cross-checks against each other: free-text Management Discussion & Analysis (MD&A) prose, written for a human reader, and structured XBRL data, tagged for machines. A company can write "revenue grew 65%" in its MD&A while its own XBRL facts imply 46.09%, and unless someone reads both and does the arithmetic, that gap goes unnoticed. It's exactly the kind of error that tends to precede a restatement, and it's invisible at scale because checking it by hand doesn't scale. I built a system to make that check economical enough to run on every filing, not just the ones already under scrutiny.

Architecture: four pillars

The bootcamp's capstone required a Bring-Your-Own-Project spanning four pillars instead of one of six provided briefs. I designed the pipeline as a deterministic, non-looping sequence so each pillar has a clear, auditable job:

PillarWhat it does
MCP toolsThree independent servers: a Filing Retriever (EDGAR 10-K/10-Q + XBRL company facts), an MD&A Extractor (prose with citations), and a Numerical Reconciler (four comparison types: absolute, growth %, absolute change, bps change)
DSPy optimizationA ChainOfThought signature for claim extraction, tuned with BootstrapFewShot / GEPA against a held-out, hand-labeled ground truth with explicit noise-floor checks
Multi-agent orchestrationA hierarchical Coordinator → Extraction Agent → Verification Agent → Reconciliation pipeline that never loops back, with budget enforcement and checkpoint/resume so a crash mid-run doesn't lose progress
RLVR / GRPO fine-tuningQLoRA (rank 32, via Unsloth) on Qwen2.5-7B-Instruct, trained on a single RTX 4090 with a reconciler-derived reward signal across 1,300–2,730 GRPO steps

The pipeline itself runs as seven deterministic stages: Filing Retriever → MD&A Extractor → Coordinator (budget and checkpointing) → Extraction Agent (DSPy ChainOfThought) → Verification Agent (concept resolution) → Numerical Reconciler → a cited report.

Key engineering decisions

The Reconciler is deterministic code, not an LLM judgment call, on purpose. I tested a naive LLM-only judge against it head-to-head: the deterministic reconciler won 15 of 15 adversarial test cases with zero false-"consistent" verdicts, versus 49% accuracy for the LLM-only approach on the same real restatement data where the deterministic version hit 96.7%. Letting a model eyeball whether two numbers "basically match" turned out to be far less reliable than just doing the math.

Fact matching is bitemporal: every XBRL value is resolved as_of the filing date it's being checked against, so a later restatement's corrected numbers can't bleed backward and quietly rewrite what counted as "consistent" at the time. And extraction is reasoning-first: the DSPy signature produces a chain of thought before the structured claim, which measurably outperformed jumping straight to structured output (zero-shot F1 0.784 vs. a 0.730 hand-written baseline).

The Verification Agent's job is narrower than it sounds, and that narrowness is what makes the whole system trustworthy: on audit it hit recall 1.000 and a false-positive rate of 0.000, which puts a ceiling of 1.000 on end-to-end accuracy regardless of how good or bad the upstream extraction is. A maker/checker split, where the checker is provably strict, matters more here than a marginally smarter extractor.

Making extraction and verification better

DSPy optimization moved extraction F1 from a 0.730 hand-written baseline to 0.784 zero-shot (precision 0.763, recall 0.806); a fresh holdout of companies never touched during development showed a larger +0.355 F1 gain, the more trustworthy of the two signals since it isn't at risk of overfitting to the dev set.

RLVR/GRPO fine-tuning on Qwen2.5-7B-Instruct then closed the gap on the hardest failure mode in a system like this: calling something "consistent" when it isn't. That false-consistent rate dropped from 0.148 to 0.036, a 0.112 absolute reduction, while overall accuracy rose from 0.766 to 0.855 and output-format failures went from 1-in-304 to 0-in-304. For a verification system, cutting the rate of confidently-wrong "all clear" verdicts matters more than the raw accuracy number around it.

Results: does it catch real errors?

The test that actually matters isn't a held-out benchmark, it's whether the system would have caught real disclosure problems before anyone knew to look. I scanned 13,827 real SEC restatement fingerprints across 541 companies and matched the pipeline's extraction against 122 real prose instances tied to those restatements. Using only the data that existed at the time, contemporaneous, not retroactively corrected, the system flagged 118 of 122 (96.7%) as inconsistent before each restatement happened.

Process: finding out where it breaks

A fresh-holdout validation on AMZN and AAPL, companies never seen during development, raised extraction resolution from 13.6% to 44.1% once I started treating holdout failures as bugs to fix rather than noise to average away. A follow-up specificity check across 8 more untouched companies (ADBE, CRM, ORCL, CSCO, INTU, IBM, QCOM, TXN) surfaced and fixed 11 separate root causes, string-matching ambiguity, unit bugs, bitemporal logic errors, period-selection bugs, and XBRL concept retagging among them, none of which showed up on paper until the system met filings it hadn't been tuned against.

Every remaining limitation is documented rather than hidden: segment-level claims that can't be resolved without dimensional XBRL tagging, calendar-month quarters that aren't parsed yet, and open GAAP/non-GAAP ambiguity in some MD&A language. The "unverifiable" verdict exists specifically so the system says so instead of quietly guessing.

What I'd take into the next project

The most valuable failures in this project came from bitemporal logic and XBRL tagging edge cases that no amount of reasoning on paper would have surfaced, only running the system against real, unseen filings did. That's the same lesson as the NBA project's walk-forward backtest, but sharper here: a maker/checker split with a provably strict checker can put a hard ceiling on how wrong the whole system can be, even when the maker (extraction) is still imperfect. I'd reach for that pattern again anywhere the cost of a confident false negative is high.
