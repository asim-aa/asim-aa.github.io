Multi-Agent Vacation Planner

A LangGraph trip-planning system that went from a mock-data demo to four live, keyless data sources, at zero ongoing API cost.

RoleSolo: orchestration design, reliability engineering
TimelineMigrated from mock-data prototype to live sources
StackPython · LangGraph · OpenAI SDK · Streamlit · pytest · GitHub Actions
Live demo Source on GitHub

Problem

Trip planning is a genuinely multi-step problem: flights, activities, and lodging all depend on each other and on budget, which makes it a good stress test for multi-agent orchestration. The first version used mock data, which is fine for testing control flow but tells you nothing about whether the system survives contact with real, messy, rate-limited APIs.

Approach & architecture

Built as a LangGraph graph: flight search and activity search run in parallel since they don't depend on each other, then a budget-dependent hotel-search stage runs sequentially once the remaining budget is known, and a final itinerary compiler assembles everything into a coherent plan. The graph structure, rather than a single monolithic prompt, is what let parallel and sequential stages coexist cleanly.

Migrating off mock data meant wiring in four live, keyless data sources at zero API cost, which meant working within the real constraints (rate limits, inconsistent response shapes, occasional downtime) that mock data hides entirely.

Key engineering decisions

Three problems showed up once real data was in the loop, and each got a targeted fix rather than a workaround. A third-party scraping library had a parsing bug that silently discarded valid results, silent failures are worse than loud ones, so I diagnosed and patched it rather than adding a retry that would have masked the same bug. Airport disambiguation (cities with multiple airports, regional hub routing) got an offline resolver with hub-connection fallback, so the system doesn't depend on a live geocoding API just to figure out where "Bay Area" means. And because LLMs will confidently invent plausible-sounding place names, I added a fact-checking guard that cross-references generated output against ground truth before it reaches the itinerary.

What broke, and what it revealed

Repeat searches were the clearest before/after: identical queries were re-hitting live sources every time, adding real latency for no new information. A TTL cache brought repeat-search latency from 1.15 seconds down to effectively zero, the kind of fix that's invisible in a demo with mock data but obvious the moment real network calls are involved.

What I'd take into the next project

Mock data is useful for testing control flow but actively misleading about reliability: the real failure modes (silent parsing bugs, ambiguous inputs, hallucinated outputs) only show up once live data is in the loop, so I now try to wire in at least one real data source as early as possible rather than perfecting the mock-data version first.
