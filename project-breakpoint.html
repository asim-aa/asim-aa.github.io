Case Study · Sep 2026

Breakpoint

An adversarial code-verification system where two different LLMs argue over correctness and a real sandboxed subprocess, not a third model's opinion, decides who's right.

RoleSolo: system architecture, adversarial pipeline design, sandbox security engineering
TimelineSelf-directed project, Sep 2026
StackPython · LangGraph · OpenRouter · Docker · Node.js · SQLite · Flask · pytest · GitHub Actions
Watch the demo Source on GitHub

Problem

Most "AI writes code" demos verify correctness by asking a language model whether the code looks right. That's judgment layered on judgment, no more reliable than asking a model to grade its own homework, and it fails silently: a same-model self-check will confidently call broken code "correct" because nothing ever actually ran it. I wanted a system where a verdict is never "the model said so." So Breakpoint replaces the opinion with an experiment: a second, genuinely different model tries to break the first model's code with real tests, and those tests execute for real, in an isolated sandbox, with no network access and a hard timeout. Pass or fail is a fact, not a vibe.

Architecture: six stages, one conditional edge

Built as a LangGraph StateGraph: a request flows through six stages, with one retry loop that's what actually makes this a system rather than a straight-line pipeline.

StageWhat it does
FramerTurns a plain-English request into a formal JSON spec: inputs, output, constraints, examples
ProverImplements the spec. Retries internally against a real compile() / node --check guard if a reasoning model leaks prose instead of code
SkepticA genuinely different model than the Prover, enforced by an assert at runtime, writes adversarial tests aimed at empty input, boundaries, and anything the spec implies but the code might not handle
SandboxExecutes every test for real, in Docker when available, a bare subprocess otherwise
ValidatorJudges whether a failing test is a real bug or itself broken, a free local syntax check first, one LLM call only if that passes
ArbiterProduces the final verdict, a confidence score, and a persisted SQLite record of every attempt

Every round re-runs every previously-generated test, not just the newest, so a fix can never silently reintroduce a bug that was already caught. The retry loop is bounded by a round budget, so a genuinely hard bug the Prover can't fix in time still produces an honest "unresolved" verdict instead of looping forever.

Key engineering decisions

A failing test isn't automatically a real bug, and treating it as one nearly broke the system: on one run, the Skeptic wrote a syntactically invalid test (a walrus operator misused inside a bare assert) alongside a mathematically false assertion. Rather than recognizing the test itself was bad, the Prover special-cased the exact failing input instead of fixing the algorithm, and the invalid test then failed identically every round with no way to ever satisfy it, permanently blocking convergence. I built a dedicated Validator node to fix this at the root: a free local syntax check catches broken tests for $0, and anything that compiles but might still be semantically wrong gets one LLM call judging the test against the spec, never the implementation.

The sandbox itself went through the same honesty standard. It now runs generated code inside a locked-down Docker container when one's available, no network namespace at all, every Linux capability dropped, a read-only root filesystem, cgroup-enforced memory/CPU limits, and the image pinned by a digest fetched live from the registry, not a bare tag that could be silently republished. When Docker isn't reachable it falls back to a bare subprocess, and every result carries an isolation field so which boundary actually ran is never hidden. Three tests prove the isolation guarantees for real, not just in configuration: a live network call, a filesystem write outside the sandbox, and the process's own uid each fail from inside the sandboxed code, skipped locally where Docker isn't installed but run for real in CI.

Extending it to a second language

The whole pipeline now targets JavaScript as well as Python, not through a parallel implementation but a single language parameter threaded through every node: camelCase spec inference instead of snake_case, a Node-assert test harness instead of pytest-style asserts, and the same Docker-or-subprocess sandbox pointed at a digest-pinned node:20-slim image instead of python:3.12-slim. Run live against a real spec, not just unit-tested against mocks, it produced a correct implementation, 14 real adversarial tests, and a clean convergence, with one test correctly excluded by the Validator for a stray markdown-fence artifact in its own extracted source, exactly the invalid-test class the Validator exists to catch.

Results: does the adversary actually catch more than a self-check?

The eval's whole point is a head-to-head: the same Prover code, judged two ways, one round of real adversarial execution versus a same-model self-check that never runs anything.

190Automated tests
13Real bugs found & fixed live
2/6Python: bugs caught, baseline missed both
2/5JavaScript: bugs caught, baseline missed both

In both languages, on the identical problem set, a non-adversarial self-check said "correct" on implementations that real, executed tests proved were buggy, the exact failure mode this project exists to replace. The JavaScript run is honestly missing one problem: the Skeptic model exhausted its retries returning empty content even at an 8,000-token budget, a real, reproducible limitation of that specific free-tier model, not a bug in Breakpoint, and it's documented as a stated gap in the report rather than silently dropped.

Live example: a classic off-by-one, caught blind

I planted a genuine bug in a scratch file with no hint left for the model: a binary search using lo < hi instead of lo <= hi, which silently misses the target whenever the search narrows to exactly one remaining index.

TestVerdictWhy it fails
Target in the middlePassLoop narrows correctly before hitting the edge case
Single-element arrayFaillo == hi on entry, loop body never runs
Target at the last indexFailSearch narrows to exactly that index and exits without checking it
Duplicate values at targetFailSame off-by-one, surfaced through a second boundary shape

The live Skeptic, working blind, wrote adversarial tests that caught 4 real failures, every one a boundary case that specific bug actually breaks, and did it against the real GitHub Action integration end to end, not a synthetic test harness.

Process: finding out where it went wrong

An adversarial LLM pipeline surfaces failure modes a happy-path demo never shows, and I kept every one of them documented rather than quietly patched. Early on, sandbox_node handed the Prover a useless "exited with code 1" on every retry instead of the real traceback, because the error-priority logic never actually fell through to stderr, the Prover was retrying completely blind until I fixed the diagnostic order. The GitHub Action integration crashed on its very first live trigger: verified against mocks but never against a real OpenRouter call, the Skeptic burned its entire token budget on internal reasoning before writing any output, and the per-file loop had no error handling at all, so one bad response took the whole Action down. I widened the retry budget, added a specific retry path for that failure, and gave the loop the same per-file resilience the eval runner already had, then re-triggered it live twice more to confirm the fix, both runs hit a real Nvidia outage and both degraded to a clean skip instead of crashing again.

Extending to JavaScript surfaced its own class of bugs: a stray non-string element in the Skeptic's JSON output that crashed extraction outright, a model that ignored the "respond with JSON" instruction entirely and just wrote plain test source, and a reasoning model leaking pure prose into the Prover's code field with no guard to catch it, since Python's compile() check had no JavaScript equivalent yet. Each is fixed and each fix is tested against the real failure that motivated it, not a hypothetical.

Product lens: what I optimized for

Every design decision here traded elegance for legibility about failure. The sandbox always reports which isolation backend actually ran instead of presenting a uniform interface that hides a silent downgrade. The eval runner refuses to overwrite a real, previously-earned report with an empty one, a rule that exists because a same-day retry once did exactly that after hitting a rate limit, caught immediately because the report is treated as data worth protecting, not a disposable log line. And the whole project runs at $0, on free-tier models exclusively, which forced real resilience engineering, quota-aware retries, honest partial reports, graceful degradation on provider outages, that a paid API budget would have let me paper over.

What I'd take into the next project

The most valuable bugs here never showed up in a design review, only running the system against a real provider, a real sandbox, and a second language surfaced them. That's the same lesson underneath the maker/checker split in the Disclosure Verifier: a system that states its own limitations and refuses to fabricate a clean number is more trustworthy than one that looks polished until you actually run it. I'd build the honesty in from the start again, an isolation field, a stated gap in an eval report, a Validator that exists specifically to say "that test doesn't count", rather than add it after the fact.
