Case Study · Sep 2026

AI Sentinel

A reliability engine for AI services that detects failures, works out which pipeline stage caused them, and verifies its own fixes, graded by a blind fault-injection eval that exposed a bug in its own detector.

RoleSolo: system design, evaluation design, reliability engineering
TimelineBuilt and hardened over about a week, Sep 2026
StackPython · FastAPI · OpenTelemetry · SQLite · pytest · systemd
Source on GitHub Architecture diagrams

Problem

Detecting that an AI service is unhealthy is the easy part: a 503 or a slow p95 will tell you that much. The harder, less-built layer is working out why it degraded and what is safe to do about it. I wanted to build that whole loop end to end (detect, diagnose, remediate, verify, remember), and to test it honestly, because a diagnosis engine that has never been graded against a fault it wasn't told about is just a set of plausible rules.

Approach & architecture

Two processes sharing one SQLite file, with no collector: a small instrumented demo AI service (auth, retrieval, LLM call, and tool call, each an OpenTelemetry span, with a switch that injects real faults) and the engine that watches it. Six threshold detectors compare a 90-second recent window against a 900-second baseline, and a per-stage correlator names which pipeline stage deviates most.

Every incident carries a recommended action, but nothing executes until a person clicks it. After an action runs, the system sends probes, compares the incident's own metric before and after, and either marks the fix verified or rolls it back automatically. Verified fixes are stored as fixtures that can be replayed later, so a change that quietly breaks a working fix gets caught. I deliberately did not build an auto-triggering circuit breaker: an action that fires on detection without a human would undercut the co-pilot-not-autopilot design the rest of the system depends on.

Key engineering decisions

The eval is blind: the fault is chosen by the eval and never told to the detection or diagnosis code, which only see spans, exactly as they would for a real incident. Each trial is scored correct, wrong stage, inconclusive, or not detected. I kept a fault type in the pool even while it scored inconclusive on every trial, because it corrupts output text without marking a span as an error and so gave the per-stage comparison nothing to attribute. Excluding it would have made the accuracy look better than the system was; instead the eval quantified the gap and I fixed it.

The eval also runs the real, unmodified detection windows, so trials have to be spaced about 100 seconds apart. Back-to-back trials let one trial's clean traffic dilute the next trial's genuine 70% error rate down to about 22%, just under the significance threshold. Narrowing the window for the eval would have tested a different code path than a real incident goes through, so I paid the wall-clock cost instead.

A second eval has a real model judge whether each response actually addresses the question. It has no mock fallback: faking semantic judgment would be dishonest, so it raises a clear error when no judge model is configured.

What broke, and what it revealed

A single 5-trial pass scored a perfect 5/5, which I knew was too small to mean much. Run at real scale, 50 trials with 10 per fault type, it scored 68%: a clean 10/10 on the three faults whose detectors only read the recent window, but 2/10 on the two that depend on a baseline.

The cause was in my own fix for an earlier bug. To stop a long-running fault from aging into its own baseline, the system excludes an open incident's time range from the baseline query. That range ran to "now" with no upper bound, so incidents nobody resolved kept excluding more of the baseline every sweep, until four of them swallowed it entirely and the latency detector went blind to any later fault. A run shorter than about 15 minutes can't hit this, which is why the small pass never saw it.

Two caveats belong next to that number. It is not a held-out estimate, since each fix targeted the previous run's misses, and 49/50 is consistent with a true accuracy anywhere from about 90% to 100%. The one remaining miss is a low-error-rate case where only 2 of 6 probes errored: the detector fired but attributing a stage isn't significant at that rate, which is a sensitivity limit of the diagnosis that I left as it is.

What I haven't verified

It watches one demo service with threshold detectors, not anomaly-detection models. The Claude and OpenAI failover paths, the LLM judge, and an OpenAI-compatible backend I added are tested with mocked SDK calls only; no live provider call has run, and the README says so. It runs locally with one command and persistently on a shared GPU cluster (user-level systemd, no sudo), but there is no public live demo.

Product lens: what I prioritized

I prioritized being able to trust the system over making it look impressive. "Verified" means real post-action traffic confirmed the metric recovered, and if it didn't, the system reverts itself and says so. I reported the eval's failures instead of dropping the faults it failed on, and kept the caveats next to the headline number, because a reliability tool that overstates its own accuracy defeats its purpose.

What I'd take into the next project

A passing small eval is a claim about the eval, not the system: the failure modes lived at a scale the first pass never reached. I now run an eval at the size where failures show up, re-run it after every fix because each fix can expose the next layer, and write down what the number does and doesn't prove before anyone else has to ask.
