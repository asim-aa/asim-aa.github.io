GroundedIQ: Evidence-Grounded Analytics Copilot

An analytics copilot that answers business questions with deterministic SQL and Python, not a free-form LLM guess, with evidence and explicit warnings attached. Now publicly deployed with the LLM demoted to an optional layer: if it's unavailable, the app still answers from verified evidence.

RoleSolo: data modeling, text-to-SQL, guardrail design
Timeline7 Olist e-commerce datasets integrated
StackPython · SQL · DuckDB · Pydantic · OpenAI SDK · Streamlit · Plotly
Live demo Source on GitHub

Problem

Ask a general-purpose LLM a business analytics question and it will happily answer in prose, with numbers it may have partially invented. For anything that needs to be defensible, revenue by region, order fulfillment trends, that's the wrong shape of answer. What's needed is a system that turns the question into actual queries against actual data, and shows its work.

Approach & architecture

Seven Olist e-commerce datasets were integrated into a single validated DuckDB analytical model, 112,650 rows, with schema checks and explicit table grain defined up front, so every downstream query is working against a model that's been checked for consistency rather than raw, unvalidated tables.

A natural-language question is converted into deterministic SQL and Python rather than answered directly by the model. The generated query runs against the validated model, and the response is built from the actual query result plus an evidence-backed summary, including explicit warnings when the question can't be answered cleanly from the available data. Conversational follow-ups get rewritten with the prior context so a user can refine a question without restating it from scratch.

Key engineering decisions

The guardrail layer is the core design choice: safeguards against invalid aggregation catch cases where a generated query would silently produce a misleading number (double-counting a join, aggregating at the wrong grain) before that number ever reaches the user. Pydantic schemas enforce structure on both the generated query plan and the final response, so malformed output fails loudly during development rather than shipping a plausible-looking wrong answer.

What broke, and what it revealed

Early iterations without explicit table-grain checks would occasionally aggregate at the wrong level: a subtle bug that produces a number that looks reasonable but is quantitatively wrong. Making table grain an explicit, checked property of the schema (rather than an implicit assumption) turned that class of bug into a validation failure instead of a silent wrong answer.

Built with Streamlit for the interface and Plotly for visual output, backed by 42 automated tests covering the query-generation, guardrail, and fallback logic.

Hardening for public deployment

After the initial build, I removed the explanation layer's sole dependency on an external LLM API, a single point of failure for a demo meant to be public and always reachable. The explanation step now branches off the same verified EvidenceResult: if the LLM is configured and reachable, it produces a grounded natural-language explanation; if credentials are missing or the provider fails, the app falls back to a deterministic explanation assembled directly from the same verified metrics, with nothing invented or recalculated. I added regression tests covering both the fallback path and missing-LLM configuration, then deployed publicly on Streamlit Community Cloud, which bootstraps the Olist dataset and DuckDB database automatically on a fresh instance.

What I'd take into the next project

LLM output is most trustworthy when it's constrained to producing something checkable: a query, a structured plan, rather than a final answer directly. That constraint is what makes the guardrails possible in the first place, and it's a pattern I now default to whenever an LLM is in the loop on something that needs to be defensible. The same instinct extended to deployment: treating the LLM as an optional enhancement rather than a hard dependency means the system degrades gracefully instead of failing outright when an external API is unavailable.
