Case Study · Product

Spotify Taste Pipeline

An active-learning swipe interface that learns a listener's taste from a handful of keep/remove decisions, so cleaning up a stale Spotify library doesn't mean reviewing the whole thing.

RoleSole builder — product decisions, engineering, and evaluation
Scale539 real saved tracks, self-labeled across three rounds of swiping (35 → 105 → 198 labels)
StackPython · scikit-learn · Streamlit · Spotify Web API · GitHub Contents API
Live demo ↗ Source on GitHub ↗

Problem

My Spotify library had grown to hundreds of saved tracks — liked songs, saved albums, followed playlists — with no realistic way to review it. Scrolling and manually deleting doesn't scale past a couple hundred items, and Spotify itself gives you no tool for triaging a bloated library. The only "declutter" workflow available is unlink everything and start over, which throws away years of good data along with the noise.

I framed the opportunity as a product question rather than a modeling one: can a small amount of a user's own feedback (a swipe-to-keep/remove interface) teach a model to predict what the rest of their library should do, so the user reviews less than their whole collection to get most of the benefit?

Users & success criteria

Primary user: a listener with a large, stale Spotify library who wants it cleaned up without a manual pass through every track. I defined success along two axes going in: learning efficiency — does a classifier trained on the user's own swipes beat a naive majority-class baseline, and does it keep improving as more labels come in — and real usage, not a demo — the tool had to work against a live account with real data, not a mocked dataset, and had to survive being handed to other users, not just me.

Prioritization decisions (and what I said no to)

The feature set was dictated by a moving platform, not by choice. My original plan used Spotify's audio-features endpoint (energy, valence, danceability) — the obvious signal for a taste model. Spotify deprecated that endpoint for new apps in Nov 2024 and killed preview_url alongside it. The remaining option, genre from the artist endpoint, turned out to be gated behind Extended Quota Mode, which requires a registered business and 250k+ monthly active users — not a real path for a single-user portfolio project. I dropped genre entirely rather than chase an approval I couldn't get, and rebuilt the feature set around what was actually available: track and album metadata, recency (days since added, play recency), and co-occurrence signals (playlist count, same-artist saves).

I chose an active-learning swipe loop over labeling the whole library up front. The product bet was that a user's tolerance for manual review is low, so the interface needed to ask for feedback on the most informative tracks first, not a random sample. That's a direct tradeoff of engineering complexity (active learning is harder to build and validate than a static labeled set) against user effort — I prioritized the harder build because the value proposition collapses if the user has to swipe on everything anyway.

I split "real data" from "demo data" when I opened the tool to other users. Multi-user deployment on Streamlit Cloud was capped at 5 testers by Spotify's Development Mode limit, and I decided the owner's real swipe history should never mix with a tester's session: testers get the full real experience against their own Spotify account, but their swipes are session-only and never written to my dataset. It would have been faster to log everyone's swipes to one file, but it would have corrupted the one dataset the model actually depends on.

I added a durability fix only after recognizing the risk, not before. Streamlit Cloud's filesystem doesn't persist, so the deployed app's labels.csv would reset on redeploy — meaning live labeling could silently vanish. I built a GitHub Contents API sync (auto-commit every 10 labels, plus a manual "sync now" button) and tested the failure mode directly: a simulated conflicting write (stale SHA) was correctly rejected instead of overwriting good data. I also hit and fixed a real near-miss during testing where I briefly overwrote real label files myself — caught via git before anything was lost.

Model choice was decoupled from reporting. RandomForest stayed the model driving the live active-learning loop since it was already integrated and validated, but I added a logistic regression comparison purely for the writeup once I had enough labels to make the comparison meaningful — I didn't rip out a working production path to chase a half-point of reported accuracy.

What I cut

Genre and popularity features — blocked by Spotify's Extended Quota Mode requirements, documented as a known limitation rather than worked around with a fake proxy. A visualization-only "lite" version (PCA/t-SNE clustering of the library colored by keep/remove, no model) was considered as a lower-effort alternative early on, and dropped once the active-learning version proved feasible, because it would have answered "what does my library look like" but not the actual product question, "what should I do with it."

Results

539Real saved tracks evaluated
198Self-labeled swipes at final checkpoint
68.6%Accuracy at 198 labels (vs. 58.6% baseline)
+20.0 ptsBest lift over baseline, at 35 labels

Validated against my own real Spotify account and real self-labeled swipes, not synthetic data, across three checkpoints: at 35 labels, RandomForest hit 74.3% accuracy against a 54.3% baseline (+20.0 pts); at 105 labels, 62.9% against 52.4% (+10.5 pts); and at 198 labels, logistic regression overtook RandomForest as the better model at 68.6% against a 58.6% baseline (+10.0 pts). The lift shrinks as the label count grows because the class split moves closer to 50/50 — the early swipes were an easier, more lopsided sample — a real finding about how this kind of self-labeled data behaves, not just a number that goes up over time.

The two models also disagreed on which signals mattered most: RandomForest weighted recency features (days_since_added, release_year) most heavily, while logistic regression's strongest coefficients were play_recency_days and playlist_count. Across both, artist_track_count was the most consistent signal — tracks from artists the user has saved many times before were kept far more often (10.2 average same-artist saves for kept tracks vs. 1.6 for removed). I also shipped and live-verified two derived features beyond prediction: one-click unsave/remove that writes back to the real Spotify library, with idempotency verified (a repeat run added zero duplicate changes), and an album-consolidation tool that merges small saved albums into a single playlist without ever auto-removing the source album.

What I'd do differently

Start the durability/sync design before opening the tool to any other user, not after — I got lucky that the near-miss during testing was caught before real data loss. Collect labels in a more balanced way from the start, mixing old and recently-added tracks deliberately, rather than letting the natural order of the swipe queue skew the early sample, since that's what caused the lift to look artificially strong at 35 labels. And decide the model-selection criteria — accuracy vs. interpretability vs. production stability — before running the comparison, rather than after; it happened to be a clean story here, but that was partly luck.
